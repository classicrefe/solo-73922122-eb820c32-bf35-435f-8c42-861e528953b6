# 馆藏目录抽检 API

馆藏目录换版后，质检员接着核对各分馆题名。本服务用 FastAPI + SQLite 实现抽检流程：
开单（固定随机种子 + 每馆名额）→ 整版换版 → 领单（当前名单及待查状态）→ 回报（带条目修订号）。

发放存储按规则共享：同一 `(seed, quota)` 的多张单不再逐单复制名单，共享记录按曾入选的
不同书目数增长，每开一单只增加固定大小的发放信息。

## 启动

```bash
docker compose up --build
```

服务监听 `8000` 端口，交互式文档在 <http://localhost:8000/docs>（Swagger UI，可直接试走换版与回报）。
SQLite 数据落在命名卷 `qc-data`（容器内 `/data/qc.db`），重启后沿用最近生效的名单和回报。

本地开发（不用 Docker）：

```bash
pip install -r requirements.txt
QC_DB_PATH=./qc.db uvicorn app.main:app --port 8000
```

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/orders` | 开单：`{seed, quota}`，固定随机种子与每馆名额；新开单为当前生效单 |
| GET | `/orders/active` | 查看当前生效抽检单 |
| POST | `/catalog/versions` | 换版：整版目录 `{entries: [{bib_no, branch, title}, ...]}`，原子生效 |
| GET | `/catalog/current` | 当前生效目录（含每条修订号） |
| GET | `/selection` | 领单：当前名单及待查状态（`pending`/`match`/`mismatch`），含条目修订号 |
| POST | `/reports` | 回报：`{bib_no, revision, match}`，`revision` 为领单所见修订号 |
| GET | `/reports` | 当前抽检单的回报记录及是否仍有效 |

`/selection`、`/reports`（GET/POST）支持 `?order_id=` 指定历史抽检单，缺省取当前生效单。

## 规则实现要点

- **固定随机优先级**：每条书目的优先级 = `SHA256(seed:bib_no)` 前 8 字节，只由开单种子和书目号决定，
  换版、重启后不变；换版后各馆按此优先级重选，条目不足名额则全查。
- **发放存储按规则共享**（本次优化）：
  - `rules`：同一 `(seed, quota)` 全库只存一套规则；换版时每套规则只重算一次名单，
    同规则的多张单不再各算各存。
  - `rule_bibs`：每套规则按"曾入选的不同书目"存一行（`entered_seq`/`exited_seq` 为入选/落选时的
    目录版本号，`exited_seq IS NULL` 表示当前在名单中）。只在书目入选状态变化时更新对应行，
    共享记录随曾入选的不同书目数增长，与单数无关。
  - `orders`：每单只增加固定大小的 `(rule_id, base_seq)`，`base_seq` 为开单时最新目录版本号。
  - 回报受理范围 = 当前在名单中，或 `exited_seq > base_seq`（落选发生在开单之后）——
    即"本单开出时或此后成功换版中入选过"；即使后来落选，只要书目还在目录中，
    就可凭现行修订号回报。
- **旧库兼容**：升级前逐单保存的 `issued` 记录保留为只读，仍只对原单有效，不并入共享记录；
  首次启动时自动迁移（`orders` 补列、按现行目录为每套规则回填当前名单），新单不再写 `issued`。
- **修订号单调递增**：`bib_revisions` 表记住每个书目号的历史最大修订号（含已删除条目的墓碑）。
  题名或分馆改动、删除后重新录入，修订号都只会变大、绝不复用——因此旧回报即使遇到"改回原名"
  或"原样重录"也永远对不上，一律退回。
- **回报校验**：条目须在受理范围内（见上），且回报修订号等于当前生效目录中的修订号；
  条目已删除则退回。已发条目落选但未改动仍可回报；再入选时旧结论（修订号未变）自动沿用。
- **一致性**：开单/换版与对应发放在同一事务生效，校验失败（如书目号重复）或中途出错即回滚、
  保留原状态；领单查询在同一事务里读取生效目录与回报，换版与回报交错也不会读到拼接状态。
- **持久化**：名单由"当前生效目录 + 当前抽检单"即时算出，共享发放记录、目录与回报全部落库，
  重启后按已提交的发放受理回报。

## 演示：同规则两张单的回报差异（/docs）

启动服务后，在 <http://localhost:8000/docs> 依次执行（或直接跑 `scripts/demo.sh`）。
演示假定全新数据；重复演示前请先 `docker compose down -v` 清空数据卷再重新启动。

1. `POST /catalog/versions`：A 馆 `B001/B002/B003`（书名一/二/三），B 馆 `B101`（书名十）。
2. `POST /orders` `{ "seed": 42, "quota": 1 }` → 得单 1。`GET /selection` 可见
   A 馆选中 `B002`（seed 42 下优先级最高）。
3. `POST /catalog/versions`：在 A 馆追加 `N000`（新书），其余不变 → `B002` 落选但仍在目录中。
4. `POST /orders` `{ "seed": 42, "quota": 1 }` → 得单 2（与单 1 同规则）。
   两张单 `GET /selection` 看到的当前名单相同（`N000` + `B101`），差异在回报受理范围：
5. `POST /reports?order_id=<单1>` `{ "bib_no": "B002", "revision": 1, "match": true }`
   → **201**（单 1 开出时 B002 在名单中）；
   `POST /reports?order_id=<单2>` 同样报 `B002` → **409**（单 2 开出时 B002 已落选）。
6. 两张单报 `N000`（revision 1）均 **201**（现行名单 / 开出后换版入选）。

存储侧对照：`rules` 只存一套规则；`rule_bibs` 共 3 行（B002、N000、B101，即曾入选的不同书目数）；
`orders` 两行各带固定大小的 `(rule_id, base_seq)`；旧版逐单表 `issued` 无新增。

## 自测

```bash
pip install -r requirements.txt pytest httpx
pytest tests/ -v
```

覆盖：名额与全查、名单可复现、回报受理/退回、题名或分馆改动使旧回报失效、删除重录失效、
落选可回报与再入选沿用、换版失败保留原目录、重启沿用、换版与回报交错、同规则两张单的回报差异、
共享存储增长形态、落选再入选、旧库迁移（旧记录只对原单有效）、重启后按已提交发放受理、
开单/换版失败保留原发放状态。
